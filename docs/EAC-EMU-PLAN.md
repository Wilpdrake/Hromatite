# EAC emulator — план фазы 3 (event hooks + report-level heartbeat)

Дата: 2026-11-17. База: ветка `eac-forge` (worktree `~/RustroverProjects/Hromatite-eac`),
master `78d8122`. Новая ветка: `eac-emu`.

## 0. Новое, что меняет картину (измерено офлайн сейчас)

Heartbeat — **не самостоятельный 512-Б кадр**, а фрагмент длинного потокового
отчёта, который EAC-модуль выдаёт непрерывно:

* 512-Б кадры идут каждые ~2007 мс, `Sequence` глобальная (+1 на кадр).
* Флаг `StartData` (bit0) стоит ровно **один раз на отчёт**: в `control_0009` —
  seq 1 и seq 145, т.е. отчёт = **144 кадра ≈ 70 КБ ≈ 290 с**. Других
  `StartData`/`EndData` в 14 захватах нет.
* Тело первого кадра отчёта начинается с **открытого 32-Б заголовка**
  (одинаков во всех сессиях):

```
+0x00 u32 0x638    (во 2-м отчёте той же сессии — 0x8fe)
+0x04 u32 1
+0x08 u32 nonce   (разный у каждого отчёта)
+0x0C u32 5
+0x10 u32 13 (у 2-го отчёта 4)
+0x14 u32 3
+0x18 u8  флаг    (0x16/0x93/0x23/…) — именно сюда писал forge `bump`
+0x1C u32 per-session (постоянно внутри сессии: 0x1ee3a0ff / 0xbdf49289 / …)
```

Остальные 456 Б заголовочного кадра и все 488 Б последующих — энтропия 7.5–8.
Одинаковых 16-Б блоков между соседними кадрами — **0**, между сессиями на тех же
позициях — 0/488 совпадений: либо шифр с потоковым nonce, либо реальные свежие
хеши памяти. Различить офлайн нельзя.

**Следствие для forge:** все «свои» кадры в `forge_*` были построены из шаблона
одного кадра (обычно с `StartData`) и повторяли один и тот же фрагмент → сервер
видел рваный/повторяющийся отчёт. Это правдоподобная причина отказа за 39–75 с,
не обязательно «устаревшее тело».

## 1. Цели

A. Проверить гипотезу «отчёт как поток» живым экспериментом: реплей **целого
   записанного отчёта** с перецелевой привязкой (`SessionId`/`Sequence`/CRC).
B. Сделать хук на **события VRChat (Photon)**: наблюдать весь поток событий
   (код 66 = EAC heartbeat, `OpRaise`/`OnEvent`) и уметь поднимать событие 66 из
   игрового потока — транспорт, не зависящий от EOSSDK.
C. Зафиксировать результат в `findings/` + §17 `AGENTS.md`, коммит на шаг.

## 2. Шаги (в порядке выполнения)

### Шаг 1 — оффлайн-модель отчёта (без игры)
Файлы: `~/EAC-RE/tools/report_extract.py` (новый), `findings/report_stream.md`.
- Резать capture на сообщения по `StartData`, забирать полный отчёт (в
  `control_0009` он есть целиком: seq 1..144).
- Таблицы: заголовок по всем 14 сессиям, длины отчётов, распределение флагов,
  позиционная энтропия (тест «поток vs блочные записи»), поиск магии
  (zlib/Oodle/LZ4) в теле.
- Риск: нулевой (только чтение). Проверка: скрипт печатает сводку по всем
  захватам, отчёт-артефакт сохраняется в `evidence/report_<HHMM>/`.

### Шаг 2 — live: `EAC_REPLAY_REPORT` (ветка `eac-emu`)
Файлы: `crates/hromatite-eac/src/forge.rs` (+ `replay.rs` при необходимости),
`eos.rs` (режим), тесты.
- Новый режим: файл отчёта (144 кадра) → при каждом слоте 512-Б кадра отдавать
  очередной записанный кадр с заменой `SessionId`, `Sequence`, пересчётом CRC.
- Варианты (env): `EAC_REPLAY_REPORT_FROM` (с какого кадра), `_PATCH_HDR=0|1`
  (переписывать ли 32-Б заголовок — nonce/flags оставить как есть),
  `_LOOP=1` (начать отчёт заново по исчерпании).
- Критерий успеха: сессия живёт **≥300 с** после подмены (сейчас 39–75 с).
  Негативный результат тоже результат: значит тело сессионно-привязано.
- Риск: залипание колбэка игры (см. `forge_0206`) — отправлять из тика, не из
  своего потока, если возможно.

### Шаг 3 — хук на события Photon (то, что просил пользователь)
Файлы: `crates/hromatite-core/src/raw/photon.rs` (новый, managed-хук),
`crates/hromatite-eac/src/events.rs` (лог/фильтр), проводка в `eos.rs`/`eac.rs`.
- Резолв: `m3::find("ExitGames.Client.Photon", "PhotonPeer")` →
  `m3::method_in_chain(class, "SendOperation")` → `MethodInfo+0x00` = entry.
  (Инфраструктура managed-хука и trampoline уже есть в `raw/hook.rs`,
  проверена на `LateUpdate` в живой игре.)
- Из SendOperation(`byte opCode`, `Dictionary<byte,object> parameters`,
  `SendOptions`) логировать: opCode, наличие/размер `244` (event code) и `245`
  (payload); для event 66 — hex/размер payload → сверить 1:1 с тем, что уже
  видит хук EOSSDK. Отдельный счётчик dt по коду 66.
- Входящие: `OnEvent(EventData)` (та же схема) — event 66/226/255 и прочее.
- Инъекция: `EAC_EVENT=1` — наш кадр уходит как `SendOperation(253, {244:66,
  245:byte[]}, opts)` из LateUpdate-тика (игровой поток).
- Риски: (1) класс/метод не найдётся по имени — fallback по числу методов и
  сигнатуре; (2) декодирование `Dictionary<byte,object>` (il2cpp-раскладка:
  `_count`, `entries[]`, `hashCode/next/key/value`); (3) SendOptions — структура
  по значению (проверить, приходит ли указателем); (4) хук горячего метода —
  только чтение аргументов, без блокировок, лог через ring-buffer.
- Критерий: в логе видны коды событий живой сессии; event 66 приходит раз в
  ~2 с; payload совпадает с capture EOSSDK байт-в-байт.

### Шаг 4 (опционально) — ключ
Хук на конструктор `0x180405AF0` (12-Б пролог без `rel32`) → снять 32-Б
key/IV; затем починить перелокализацию `call rel32` в `build_trampoline` и
включить 5 EVP-детуров. Риск: падение игры (уже наблюдалось).
